# 每日新闻推送（Daily News Push）

一个可以在**小米澎湃 OS / MIUI / HyperOS** 上使用的 Android 应用：每天在你指定的时间自动抓取订阅的
RSS 新闻源，并以通知的形式把当天的要闻推送到手机。

- 包名：`com.dailypush.news`　版本：1.6.0　应用名：**DailyNews**
- 支持 Android 8.0（API 26）及以上，澎湃 OS（Android 13/14）已适配
- 无广告、无服务器，所有数据都存在手机本地

---

## 一、功能

| 功能 | 说明 |
| --- | --- |
| **每日定时推送（可多个时间点）** | 一天最多设 **6 个**推送时间点（默认 08:00），例如早 8 点、午 12 点、晚 8 点各推一次；每个时间点各推各的，同一个时间点一天只推一次 |
| 三种通知方式 | 汇总成一条 / 每条单推 / 两者都要 |
| **内置 35 个订阅源** | **新华社要闻、人民日报电子版、人民网要闻** + 中新网各频道、界面新闻、东方财富、华尔街见闻、IT之家、少数派等 + **机核 / IGN中国 / 游研社（游戏）** + **微博/百度/抖音/知乎/B站/头条/腾讯 7 大热搜榜 + B站热门视频** |
| 自由增删订阅源 | 任何 RSS / Atom 地址都能加进来，支持先「测试」再添加 |
| 抓取健康度 | 「订阅源」页会显示上次抓取成功/失败的源数量，失效的源一眼可见 |
| 热搜榜 | 微博、百度、抖音、知乎、B站、今日头条、腾讯新闻 7 个平台的实时热搜 + B站热门视频，单独分区展示；**能打开原文的标原文、只有关键词的标「搜索」** |
| 要闻列表 | 按「今天 / 昨天 / 更早」分组，**每一天下面再按新闻分类分组**（时政 / 要闻 / 国际 / 财经 / 社会 / 科技 / 生活 / 游戏），每条卡片上带分类标签，点标题直接用浏览器读原文 |
| **回到顶部** | 列表往下滚一点，右下角浮出「回到顶部」按钮；**点顶部标题栏也能一键回到最上面**（要闻 / 订阅源 / 今日 / 痕迹 四个页都有） |
| **AI 自动配置** | 接入 MiniMax API，用一句大白话描述需求（"每天8点10条国际科技新闻带热搜"），AI 自动解析成数量、时间、内容分类、关键词并应用到推送 |
| **AI 合并重复报道** | 推送前让 AI 判断哪些新闻在讲同一件事，合并成一条推送，其余折叠在「今日」页里（各家原文仍可点开） |
| **今日推送页** | 独立页面列出今天到底推了什么，每条都能一键打开各家原文 |
| **决策痕迹** | 随时查看今天的选稿过程：有哪些新闻、选了哪些、每一条为什么选 / 为什么没选；**只存在本地，不会推给用户** |
| 推送体检（助手页） | 一键检查通知权限、精确闹钟、电池白名单、自启动，并直接跳到系统对应页面 |
| 免打扰友好 | 抓取期间只显示一条最低优先级的临时状态通知，抓完即消失 |
| 点通知直达 | 点开推送通知直接进「今日」页，看当天推了什么 |

### v1.5.1 修正：关键词是「重点关注」，不是过滤器

旧版把关键词当成了**硬过滤器**：只要有一条命中关键词，整份推送就只剩命中的那几条，
其它内容全被丢掉（用户原话：「不是说只推我所筛选的这些关键词，而是说重点是这些东西」）。

现在的语义：

| 配置项 | 含义 | 效果 |
| --- | --- | --- |
| **内容分类** | 「我还想要哪些类别」（不选 = 不限） | 选中的**每一个分类都会出现在推送里**，名额按分类轮流分配，不会被条目多的分类吃光 |
| **重点关键词** | 「这些内容如果出现了，**一定要推**」 | 命中的条目标成「重点」，**优先推送并保证有名额就一定入选**；一条都没命中也**完全不影响**其它内容照常推送（不筛、不报错、不推空） |
| **附带热搜榜** | 推不推热搜 | 热搜有独立配额（每平台 3 条、总共 12 条），不占新闻名额 |

另外顺带修了一个真 bug：**分类过滤之前是用「源名」反查分类的**，
而 RSS 抓取时 `Article.source` 存的是**频道标题**（「中新网时政新闻」），
和订阅源名字（「中新网·要闻」）对不上 → **一选分类，普通新闻会被全部过滤掉，只剩热搜**。
现在改成抓取时就把分类写进数据里（`Article.category`），老数据再退回按源名反查。

「今日」页里命中的重点条目会带一个「重点」小标签。

### AI 解析为什么偶尔失败（v1.4.1 修的坑）

「测试连接」成功但「AI 解析」失败，最常见的三个原因：

1. **输出上限太小，JSON 写到一半被截断**。
   推理模型（M1/M2/M3）的**思考 token 也算进 `max_completion_tokens`** ——
   官方示例里一句「你好」就用了 223 个 token，其中 214 个是思考。
   旧版给解析只留了 1024，很容易写不完就被砍断。
   现在解析留 **8192**，失败重试时再翻一倍。
2. **推理模型对 `temperature` 有额外要求**。官方推荐 M2/M1 用默认值，
   传 0.2 之类的可能被判参数非法。现在**推理模型不发 `temperature`**。
3. **模型的 JSON 写法不规范**：数字写成字符串（`"maxItems":"8"`）、少给字段、多给未知字段。

对应措施：

| 措施 | 说明 |
| --- | --- |
| 宽松解析 | 逐字段手动取值，容忍类型不符、缺字段、多余字段 |
| 截断修复 | JSON 被砍断时，自动补齐括号、逐字回退重试 |
| 失败重试 | 第一次不成，自动用「只输出 JSON」的严格提示再来一次，上限翻倍 |
| 错误可见 | 还是失败时，错误信息里会带上模型原始回复的前 300 字，方便反馈 |

另外 v1.4.1 起，**「设置 → 推送内容筛选」可以直接手动改**：分类多选、关键词输入框、附带热搜开关。
AI 解析只是省事，不是唯一入口——AI 挂了不影响你把推送配好。

### AI 自动配置（MiniMax）

「AI」页做两件事：

**一、填接口**（默认值就是 MiniMax 国内站）

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| 接口地址 | `https://api.minimaxi.com/v1` | 海外站账号改成 `https://api.minimax.io/v1`；任何 OpenAI 兼容接口也能用 |
| API Key | 空 | 在 platform.minimaxi.com 控制台创建；**用加密存储只存在手机里** |
| 模型 | `MiniMax-M3.1-Flash` | 官方当前支持 MiniMax-M3.1-Flash 与 MiniMax-M3；老的 M2 / M1 / Text-01 也能填。也可以点「**查看可用模型**」直接读出这个 Key 真正能用的模型名 |

填完点「测试连接」验证通不通，也可以先点「**查看可用模型**」——它会去调 `GET {base}/models`，
把**这个 Key 实际能用的模型名**列出来（点一下直接填进模型框）。这同时也是最快的排查手段：
连不上时，就能立刻分辨是 Key 无效、地区不对，还是模型名写错。

失败时 App 会把**每个端点的错误分别列出来**，并附中文提示。

**App 依次尝试的端点**（第一个成功就停）：

| 顺序 | 端点 | 说明 |
| --- | --- | --- |
| 1 | `{base}/chat/completions` | OpenAI 兼容，官方推荐的新接入方式 |
| 2 | `{base}/anthropic/v1/messages` | Anthropic 兼容，**Token Plan（sk-cp-）的 Key 常常只能用这条路** |
| 3 | `{base}/text/chatcompletion_v2` | MiniMax 原生，官方已标为废弃，只作兜底 |

> **关于「余额不足」（1008）**
> MiniMax 有两套**互不通用**的 Key：
> - `sk-api-` 开头的**按量付费 Key**，扣账户余额 → 余额不足要去控制台充值；
> - `sk-cp-` 开头的 **Token Plan 订阅 Key**，扣套餐额度 → 额度按 5 小时滚动窗口重置，套餐到期或没分配席位就会报「余额不足」。
>
> 另外**地区必须匹配**：国内站 `platform.minimaxi.com ↔ https://api.minimaxi.com/v1`，
> 海外站 `platform.minimax.io ↔ https://api.minimax.io/v1`，两站 Key 不能互换。
>
> 如果你的这个 Key 在别的平台能用同一个模型跑通，最省事的做法是：
> 把「接口地址」和「API Key」都换成那个平台的值——本 App 支持任何 OpenAI 兼容接口。

> **必须带一条 user 消息**：MiniMax 网关只把 user 消息里的内容当作「chat content」，
> 如果 `messages` 里只有 system 消息（或 user 的 content 为空），接口会直接拒绝：
> `invalid params, chat content is empty (2013)`。App 里所有请求都强制补上了非空的 user 消息。

> **超时**：M1 / M2 / M3 是推理模型，思考时间长。AI 请求用了单独的客户端，读超时放宽到 150 秒（抓新闻那套 30 秒超时会经常被掐断）。

**二、用大白话说需求**

```
每天早上8点给我10条国际和科技新闻，另外带上热搜
```

点「AI 解析」，模型会回一段结构化配置，页面上直接展示并可手动微调：

| AI 能配的 | 取值 |
| --- | --- |
| 推送时间点 | 24 小时制 HH:mm，**可一次给多个**（早中晚），最多 6 个 |
| 条数 | 3~40 |
| 内容分类 | 时政 / 要闻 / 国际 / 财经 / 社会 / 科技 / 生活 / **游戏** / 热搜 |
| 关键词 | 0~5 个（只推标题命中的） |
| 含不含热搜 | 开关 |
| 通知方式 | 汇总 / 逐条 / 两者都要 |

点「应用到推送」后生效：

- 推送时按分类 + 关键词过滤（关键词一条都没命中时退回不过滤，避免推空）
- 订阅源按分类自动启用/停用，不再抓用不上的源
- 推送时间、条数、通知方式一并更新，定时任务重新排程
- 「设置」页能看到当前生效的筛选条件

提示词里带了 App 当前已有的配置和全部内容源清单，所以**你只说改哪一项，别的保持不变**。

### 为什么有的条目点开是「搜索」而不是原文（v1.4.0 修的坑）

热榜接口给的**原始链接**不一定能直接打开，各平台情况不一样：

| 平台 | 接口给的链接 | 能不能直接看内容 |
| --- | --- | --- |
| 知乎 | `api.zhihu.com/questions/{id}` | ❌ **这是 API 地址不是文章页**，浏览器打开报「请求参数异常，请升级客户端后重试」。已改成 `www.zhihu.com/question/{id}` |
| B站热搜 | 只有 `keyword`，`uri`/`goto` 都是空的 | ❌ 平台只给词，没有原文页 → 站内搜索（已标「搜索」） |
| 微博 / 抖音热搜 | 只有词 | ❌ 站内搜索（已标「搜索」） |
| 头条 / 腾讯 / 百度 | 真实内容页 / 真实链接 | ✅ 直接打开 |
| B站热门视频 | `bvid` | ✅ `bilibili.com/video/{bvid}` 直接打开 |
| 全部 RSS / 网页新闻源 | 真实文章链接 | ✅ 直接打开 |

App 现在把这两类**区分开**：能在文章页的照常显示，只有关键词的显示「站内搜索」并说明原因，
推送通知里也会标出来。`Article.linkKind` = `page` / `search`。

### 推送只有两条时的两道保险

1. **AI 分类全不匹配**：如果 AI 解析出的分类（比如它自造的「军事」）在订阅源里一个都对不上，
   旧版会把所有新闻源都关掉，只剩热搜 → 推送只剩热榜。现在会**保留全部源**并提示。
2. **AI 合并过于激进**：模型偶尔会把不相干的条目并进一组，把 20 条压成 2 条。
   现在只要合并结果少于原来的三分之一，**整份丢弃这次合并**，按原顺序推，
   并在「决策痕迹」里写明原因。

另外，「决策痕迹」里能看到完整的数字链路：抓到了多少条 → 候选池多少条 → 最终推了几条，
以及每一条被刷掉的具体原因（分类不符 / 关键词没命中 / 超过 24 小时 / 超出条数上限 / 合并掉了）。

### AI 合并重复报道 + 决策痕迹（v1.3.0 新增）

一次推送的完整链路是：

```
抓取全部源 → 分类/关键词筛选 → 只留 24 小时内的新鲜内容
            → AI 判断哪些在讲同一件事 → 每组只留一条代表
            → 按条数配额选出最终名单 → 写决策痕迹 → 发通知
```

**合并**：`AiClient.mergeSimilar()` 把候选列表（带序号）交给 AI，要求它只返回 JSON：

```json
{
  "groups": [
    {"topic": "习近平会见智利总统卡斯特", "representative": 2,
     "members": [1, 2, 7], "reason": "两家媒体报道的同一次会见，保留新华社稿件"}
  ],
  "note": "合并了 1 组重复报道，从 20 条减少到 12 条"
}
```

每组只有 `representative` 那条会被推送；组里其它来源不会丢——在「今日」页点「另有 N 家也报道了」就能看到并逐条打开原文。

**痕迹**：每次定时推送都会写一份 `filesDir/traces/YYYY-MM-DD.json`，内容包括：

| 字段 | 含义 |
| --- | --- |
| `candidates` | 送进 AI 挑选的候选池，每条带 `selected` 和 `reason` |
| `filteredOut` | 分类不符 / 关键词没命中 / 超过 24 小时的条目 |
| `selectedIds` | 实际推送出去的条目（有序） |
| `note` | AI 对这次合并的一句话总结 |
| `filterSummary` | 当时生效的筛选条件 |
| `aiUsed` / `aiError` | 有没有真的用上 AI，失败时写明原因 |

在「今日」页点右上角图标，或「设置 → 决策痕迹」进入；顶部可切换最近 30 天里任意一天的记录。痕迹**永远不会作为通知推送**，只在你主动查看时呈现。

AI 合并失败（没填 Key、断网、模型返回的不是 JSON）时会**自动退回不合并**，照常推送，同时在痕迹里写明失败原因——不会因为 AI 挂了就推不出东西。

### 五个页签

| 页签 | 作用 |
| --- | --- |
| **要闻** | 全部抓到的内容，按今天 / 昨天分组，热搜单独分区 |
| **订阅源** | 35 个内置源开关、添加自己的源、抓取健康度 |
| **今日** | 今天推了什么，逐条可开原文；右上角图标进「决策痕迹」 |
| **AI** | MiniMax 接口配置、一句话需求、AI 合并开关 |
| **设置** | 推送时间、条数、通知方式、筛选条件、助手与权限入口 |

「助手」和「决策痕迹」是二级页面，从「设置」页或「今日」页进入。

### 三种取源方式

| 类型 | 怎么抓 | 内置例子 |
| --- | --- | --- |
| **RSS** | 标准 XML 订阅源 | 中新网、界面新闻、东方财富、IT之家、少数派、Solidot…… |
| **网页** | 直接从官网页面抽取「标题 + 链接」 | 新华社要闻、人民日报电子版、人民网要闻 |
| **热榜** | 各平台自己的接口，返回热搜词条 | 微博、百度、抖音、知乎、B站、今日头条、腾讯新闻 |

「订阅源」页可以随时添加源：RSS 填订阅地址，网页填新闻页面地址，添加前都能先点「测试」确认能不能抓到。

### 为什么人民日报 / 新华社走「网页」而不是 RSS

因为**它们的官网 RSS 都已经停更**：

- 人民网各频道 RSS 停在 **2025-06-05**（能返回 100 条，但全是那一天的旧闻）
- 新华网 RSS 停在 **2022-12-14**，而且连 `<pubDate>` 标签都丢了（日期变成裸文本）
- 新浪 RSS 停在 **2018-09-23**

把这些源按 RSS 加进来，等于每天推送一年前的旧闻。所以改成直接抓官网首页 / 电子版——这两处仍然是服务端渲染，实测能拿到当天的标题和链接，且链接里带日期，App 可以准确判断发布时间。

内置 35 个源全部经过**真实抓取 + 新鲜度校验**（最新条目必须是当天）。

## 二、直接安装（最省事）

1. 把 `每日新闻推送-v1.3.0.zip` 传到手机（数据线 / 网盘 / 微信都行），用「文件管理」打开并解压。
2. 点击解压出来的 APK 安装。系统会提示「未知来源应用」，按提示允许一次即可。
3. 安装后打开应用，按「设置 → 助手与权限」的指引把 4 项权限都打开。

> 如果你用的是「澎湃 OS」，第 3 步尤其重要：不打开自启动和电池白名单，
> 系统会在息屏或清理后台时把本应用冻结，闹钟就不会按时触发。

## 三、从源码构建

### 方式 A：Android Studio（推荐）

1. Android Studio Hedgehog 或更新版本 → **Open** → 选择本项目根目录。
2. 等待 Gradle Sync 完成（首次会下载依赖，已配置阿里云镜像，国内速度较快）。
3. 菜单 **Build → Build Bundle(s) / APK(s) → Build APK(s)**。
4. 产物在 `app/build/outputs/apk/debug/app-debug.apk`。

### 方式 B：命令行

```bash
export JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64
export ANDROID_HOME=$HOME/Android/Sdk     # 换成你的 SDK 路径
cd DailyNewsPush
./gradlew assembleRelease        # 产物：app/build/outputs/apk/release/app-release.apk
./gradlew testDebugUnitTest      # 跑 RSS 解析联调测试（需要网络）
```

安装到手机：

```bash
adb install -r app/build/outputs/apk/release/app-release.apk
```

### 签名说明

项目自带签名文件，可直接产出可覆盖升级的正式包：

| 文件 | 说明 |
| --- | --- |
| `keystore/dailynews.jks` | 签名密钥（别名 `dailypush`，口令 `dailypush`） |
| `keystore.properties` | 密钥库路径与口令 |

改了代码后重新 `assembleRelease`，得到的 APK 可以直接覆盖安装升级，不会出现「签名不一致无法覆盖」。
若要换成自己的密钥，替换上面两个文件即可。

### 热榜是怎么抓的

各家热榜都不是 RSS，而是自己的接口：微博 `weibo.com/ajax/side/hotSearch`、百度 `top.baidu.com` 内嵌数据、抖音 `aweme/v1/web/hot/search/list`、知乎 `api.zhihu.com/topstory/hot-list`、B站 `api.bilibili.com/x/web-interface/search/square`、头条 `hot-event/hot-board`、腾讯 `i.news.qq.com/gw/event/hot_ranking_list`。

App 里为每家写了一个解析器，统一转成和新闻一样的条目，所以在「要闻」页里热搜是单独一个分区，在推送里也单独成段（「今日要闻 8 条 · 热搜 12 条」），不会把当天要闻挤掉。

实测注意：**微博和 B站的接口用 Android UA 请求会 403，必须用桌面浏览器 UA**，App 里已统一处理。

### 技术栈

Kotlin + Jetpack Compose (Material 3) + Coroutines + WorkManager + AlarmManager +
OkHttp + DataStore + kotlinx.serialization。Gradle 8.7 / AGP 8.5.2 / JDK 17 / minSdk 26 / targetSdk 34。

## 四、澎湃 OS 必做的四项设置

| 顺序 | 设置项 | 路径 | 为什么 |
| --- | --- | --- | --- |
| 1 | 通知权限 | 设置 → 应用设置 → 应用管理 → 每日新闻推送 → 通知管理 → 全部允许 | Android 13+ 不允许就收不到任何推送 |
| 2 | 精确闹钟 | 应用详情 → 闹钟与提醒 → 允许 | 没有它，定时任务会被系统延后甚至不触发 |
| 3 | 电池优化白名单 | 应用详情 → 省电策略 → 无限制 | 不加白名单，息屏后进程会被冻结 |
| 4 | 自启动 | 设置 → 应用设置 → 自启动管理 → 打开「每日新闻推送」 | 清理后台 / 重启手机后，定时任务要能自己恢复 |

应用内「助手」页的第 1~4 项都可以一键跳到对应的系统页面。

额外建议：

- 在最近任务界面下拉本应用卡片（或长按）选择「锁定」，避免一键清理时被杀掉；
- 省电模式关闭，或把本应用加入省电模式白名单；
- 锁屏通知设为「显示」，允许声音和震动。

## 五、推送是怎么保证到点的

1. **AlarmManager 精确闹钟** 负责准点触发（`setExactAndAllowWhileIdle`）；
   没有精确闹钟权限时自动退化为 `setAndAllowWhileIdle`，不会崩。
2. **WorkManager 24 小时周期任务**作为兜底，防止厂商系统把闹钟清掉后当天再无推送。
3. 闹钟触发后由 `NewsSyncWorker` 抓取，必要时以**前台服务**身份运行，系统不容易中途杀掉。
4. 同一天 3 小时内只会推一次，避免「闹钟 + 兜底任务」重复打扰。
5. 开机、换机、修改系统时间后自动重排定时任务（`BootReceiver`）。

## 六、常见问题

**Q：到点没收到通知？**
按这个顺序排查：
1. 打开应用「助手」页，看四项状态是否都正常（自启动那一项需要自己进系统看一眼）；
2. 「设置」页看「运行状态 → 下次推送」，确认时间对不对；
3. 手机是否开了省电模式、系统是否清理了后台；
4. 通知是否被 MIUI 的「通知免打扰」拦了。

**Q：抓到了但列表是空的？**
说明订阅源都失效了。看「订阅源」页顶部的「上次抓取：X 个成功 / Y 个失败」，把失效的关掉或删掉，再手动添加可用的 RSS 地址。

**Q：能推自己的订阅源吗？**
可以。「订阅源」页 → 添加订阅源 → 填 RSS 地址 → 点「测试」→ 确认可用后添加。任意 RSS 2.0 / Atom 都支持。

**Q：重启手机后还会推吗？**
会。应用注册了开机广播，开机会自动重排定时任务（但仍需第 4 项自启动权限）。

**Q：会不会很费电？**
每天只定时唤醒一次，抓取在几秒内完成，属于极低频任务。

**Q：推送的内容会重复吗？**
同一篇文章不会重复出现：抓取结果按链接去重合并到本地缓存；不同媒体报同一件事，
开启「AI 合并重复报道」后会合并成一条推送，其余来源折叠在「今日」页里。

**Q：点「测试连接」报错 2013 invalid params, chat content is empty？**
这是 v1.3.0 的已知问题，已在 **v1.3.1** 修好（原因见上文：请求里缺 user 消息）。

**Q：提示「余额不足」，但同一个模型我在别的平台能跑通？**
先分清是哪一种情况：
1. **Key 类型不匹配**：`sk-cp-`（Token Plan 订阅）拿到按量接口上用，会报余额不足。v1.3.2 起 App 会自动多试一条 Anthropic 兼容端点，订阅 Key 往往能走通。
2. **地区不匹配**：国内站 Key 必须配 `api.minimaxi.com`，海外站 Key 必须配 `api.minimax.io`。
3. **套餐额度用完**：Token Plan 是 5 小时滚动窗口，等窗口重置或续费即可。
4. **确实要换平台**：把「接口地址」和「API Key」换成那个能用平台的，本 App 兼容任何 OpenAI 兼容接口，模型名点「查看可用模型」确认。

**Q：连接失败怎么排查？**
v1.3.1 起失败时会把**每个端点的错误分别列出来**，v1.3.2 追加了「查看可用模型」：
先点它，如果列不出模型 → Key 或地址有问题；如果能列出但对话报错 → 换个模型名再试。

**Q：「测试连接」成功，但「AI 解析」失败？**
v1.4.1 修了最常见的三个原因（输出上限被思考 token 吃光、推理模型不接受 temperature、
JSON 写法不规范），并加了「宽松解析 + 截断修复 + 失败重试」。
如果还是失败，错误提示里会带模型原始回复的前 300 字，截个图发我就能定位。
另外**现在可以不靠 AI**：设置页的「推送内容筛选」支持手动选分类、填关键词、开关热搜。

**Q：AI 合并会不会把不同的新闻误合并？**
可能，所以合并结果可以随时在「决策痕迹」里复核：哪一组被合并了、代表是哪条、
理由是什么，都写在那里。发现合并得不合理，可以在「设置」里关掉这个开关；
另外 v1.4.0 加了保险——合并得太狠（少于原数 1/3）会自动作废这次合并。

**Q：点开推送的条目变成搜索页 / 打不开？**
v1.4.0 修了两类问题：
- 知乎之前用的是接口地址（`api.zhihu.com/questions/...`），浏览器打开必然报错，已改成真实问题页；
- 微博 / 抖音 / B站热搜这类**平台只给关键词、没有原文**，点开只能是站内搜索，
  现在会明确标成「搜索」并说明，不会再让你以为 App 出问题了。
  想要能直接打开的内容，用新增的「B站热门视频」源，或头条 / 腾讯 / 百度 / 各新闻源。

**Q：痕迹会占很多空间吗？**
每天一个 JSON 文件，只保留最近 30 天，普通一天几十 KB，可以忽略。

## 七、目录结构

```
DailyNewsPush/
├── app/src/main/java/com/dailypush/news/
│   ├── data/          数据层
│   │   ├── RssFetcher.kt        RSS/Atom 解析（系统 DOM，无第三方解析库）
│   │   ├── WebPageFetcher.kt    网页型源：抽取标题 + 链接 + 日期
│   │   ├── HotFetcher.kt        7 个平台热榜解析器
│   │   ├── AiClient.kt          大模型接口调用 + 需求→配置解析
│   │   ├── AiPlan.kt            AI 解析出来的配置结构
│   │   ├── PushFilter.kt        推送时的分类/关键词筛选
│   │   ├── PushSelector.kt     合并后的选稿与条数配额
│   │   ├── PushTrace.kt        决策痕迹的数据结构与本地存储
│   │   ├── TraceBuilder.kt     根据筛选/合并结果生成痕迹
│   │   ├── SecretStore.kt       API Key 加密存储
│   │   ├── NewsRepository.kt    并发抓取 + 去重合并
│   │   ├── SettingsRepository.kt DataStore 设置读写
│   │   ├── ArticleCache.kt      本地新闻缓存（JSON）
│   │   └── DefaultFeeds.kt      内置订阅源（已做新鲜度校验）
│   ├── work/          调度层：闹钟、WorkManager 任务、开机重排
│   ├── notify/        通知构建（汇总 / 逐条）
│   ├── ui/            Compose 界面：要闻 / 订阅源 / 今日 / AI / 设置 / 助手 / 痕迹
│   └── util/          澎湃 OS 适配、时间工具
├── app/src/test/      RSS 抓取解析联调测试（真连网络）
├── app/src/main/res/  图标、主题、网络安全配置（允许 http 明文）
└── keystore/          签名密钥
```
